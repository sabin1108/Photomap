# Supabase staging read baseline — 2026-08-13

## Scope

Production과 분리된 동일 Region Supabase staging에서 초기 사진 조회 흐름을 측정했다. 실제 사용자 데이터 대신 전용 synthetic dataset을 사용했다.

한 iteration은 다음 REST 요청 3개를 병렬 실행한다.

1. Category 목록
2. 최신 media 50개와 location, category, description 관계
3. Favorites 목록

Frontend 렌더링, Vercel CDN, Unity, Storage 이미지 다운로드, write flow는 이번 결과에 포함되지 않는다.

## Thresholds

- Checks: `>99%`
- HTTP failures: `<1%`
- p95: `<300ms`
- p99: `<800ms`
- 429: `0`
- 5xx: `0`
- Dropped iterations: `0`

Smoke p99는 작은 표본과 초기 연결의 영향을 받을 수 있다. Profile 간 p99 차이를 최적화 효과로 해석하지 않는다.

2시간 soak는 완료하지 않았다. 약 4분의 부분 실행 결과는 baseline 비교에서 제외했다.

## Database observations

| Point | Slow query entries | Peak connections | Disk | Disk IO | Memory | CPU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Before peak | 2 | 9/60 | 13% | 1% | 50% | 2% |
| After peak | 6 | 5/60 | 13% | 1% | 50% | 2% |
| After spike | 6 | 15/60 | 13% | 1% | 51% | 2% |

Dashboard 값은 rolling time window 집계다. Connection 수를 엄격한 순간 전후값으로 해석하지 않는다.

주요 PostgREST query는 평균 `0~2ms`, 최대 `2~15ms`였다. 상대적으로 느린 timezone 및 metadata query는 각각 10회 미만 호출돼 핵심 read workload 병목으로 보지 않았다.

## Conclusion

Staging은 최대 약 60 read API RPS 목표에서 오류, rate limit, dropped iteration 없이 동작했다. Spike p95는 약 `208ms`, p99는 약 `223ms`였다. CPU, memory, connection, disk IO 포화와 핵심 SQL 병목은 관측되지 않았다.

현재 수치만으로 추가 index를 정당화할 근거는 없다. 다음 측정 범위는 synthetic Storage image, Vercel Preview, Lighthouse, React Profiler, Unity 초기 로딩이다.

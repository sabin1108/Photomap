# PhotoMap 사용자 경험 성능 검증 설계

작성일: 2026-09-10
상태: 설계만 완료. 아래 목표값과 표본 수는 프로젝트 실험 규칙이며 측정 결과나 공인 기준이 아니다.

## 1. 목적과 기존 근거

가상화가 화면 요소 수를 줄이는 데서 그치지 않고, 실제 사진을 탐색하고 선택하는 과정의 지연과 빈 화면을 줄이는지 검증한다.

기존 자료: 같은 폴더의 PhotoMap-UX-performance-proof-result-2026-09-09.md.
기존 실험은 동일 SVG 반복, 독립 PhotoFeed, 데스크톱 Chromium의 모바일 viewport 조건이었다. 클릭부터 모달 이미지 준비 p95는 68.9ms→16.0ms였지만, 스크롤 차단 시간은 두 조건 모두 0ms여서 프리즈 감소를 입증하지 못했다. 모달 준비는 실제 픽셀 표시 완료와 다르다.

이번 실험은 다음 주장을 분리한다.

1. 가상화 자체가 클릭 반응과 렌더링 부담을 줄이는가?
2. 실제 이미지와 전체 앱에서도 그 효과가 유지되는가?
3. 사용자가 탐색 과제를 더 빨리, 더 적은 실패로 마치는가?

하나의 결과로 세 주장을 모두 입증했다고 쓰지 않는다.

## 2. 사전 고정할 비교 계약

- A: 현재 PhotoFeed에서 가상화만 끄고 모든 행을 렌더링.
- B: 같은 PhotoFeed에서 현재 가상화 사용.
- 같은 빌드 안에서 모드를 선택한다. 카드, store, 필터, 이미지 URL·크기·우선순위, CSS, 애니메이션, 모달 구현은 동일하게 유지한다.
- estimateSize, overscan 등은 파일럿 전에 기록하고 본 실험 도중 변경하지 않는다.
- 데이터는 모두 준비한 뒤 시작하고 hasMore=false로 고정한다. 페이지네이션은 별도 통합 실험으로 다룬다.
- PhotoFeed A/B diff를 보관한다. 가상화 외 최적화를 함께 넣으면 별도 복합 변경 실험으로 명명한다.
- 프로토콜, 실행 순서, fixture 해시, commit, 빌드 해시, 배포 URL·ID를 본 실험 전에 잠근다.
- 파일럿은 환경·계측 확인에만 사용한다. 결과가 잘 나오는 조건을 골라 본 실험 조건으로 바꾸지 않는다.
- 효과가 없거나 악화된 결과도 동일하게 보고한다.

## 3. 실제 이미지 fixture

동의받은 사진 또는 재배포 가능한 이미지로 서로 다른 썸네일 1,000개를 만든다.

- 가로·세로·정사각형, 밝고 어두운 사진, 다양한 복잡도의 이미지를 포함한다.
- 목록 썸네일과 모달 이미지는 실제 서비스의 크기·압축·선택 정책을 따른다.
- 파일별 ID, 크기, 해상도, 포맷, SHA-256, 라이선스 또는 사용 권한을 manifest에 기록한다.
- 위치·인물 등 개인정보가 포함된 EXIF는 제거한다.
- 3,000개 부하 조건에서 파일을 반복하면 고유 이미지 수와 항목 수를 별도로 명시한다.
- 검색어·앨범·정렬·선택 대상과 데이터 seed를 고정한다.
- 실제 사용자 사진을 외부 저장소나 공개 Preview에 무단 업로드하지 않는다.

## 4. 단계별 환경

| 단계 | 환경 | 검증 목적 |
|---|---|---|
| 1 | 독립 PhotoFeed, 실제 썸네일, 고정 Chromium | 가상화만의 인과 비교 |
| 2 | 전체 앱, 동일 fixture, 지도 등 함께 동작 | 통합 시 효과·회귀 확인 |
| 3 | 실제 중급 Android 기기, Chrome, 터치 입력 | 실제 모바일 재현 |
| 4 | 실제 사용자의 정해진 탐색 과제 | 완료 시간·실패·주관적 불편 확인 |

단계 1의 기본 조건은 1,000개, 390×844 CSS px, DPR 2로 한다. 3,000개와 데스크톱은 확장 조건이며 따로 집계한다.

기기 모델, SoC, RAM, OS, 브라우저 정확한 버전, 화면 주사율, 전원·절전 상태, 배터리·발열 상태를 기록한다. 실기기의 viewport는 실제 값을 기록하고 억지로 데스크톱 조건과 동일하다고 취급하지 않는다.

데스크톱 CPU 감속은 실기기 성능과 동일하지 않다. 감속 없음과 CPU 4배 감속을 별도 조건으로 보고한다. 실기기 결과에는 같은 감속 계수를 중복 적용하지 않는다.

네트워크 제한 조건은 RTT 150ms, 다운로드 1.6Mbps, 업로드 0.75Mbps로 고정할 수 있다. 이는 프로젝트용 제한 환경이며 일반적인 모든 4G를 대표하지 않는다. 실제 적용 도구와 실측 처리량·지연을 기록한다.

동시 실험은 1개, 동일 전원 상태로 실행한다. 기기 온도가 기준 범위를 벗어나면 중단하고 안정화 후 재개한다. 온도 센서 접근 불가 시 그 한계와 대기 규칙을 기록한다.

## 5. 캐시 조건 분리

- Cold browser: 새 프로필 또는 검증된 브라우저 캐시 초기화, 해당 이미지 미방문.
- Warm: 동일 탐색 경로를 예열하고 필요한 이미지의 준비를 확인한 뒤 복귀.
- 브라우저 HTTP 캐시, 서비스 워커, CDN 캐시는 각각 기록한다.
- 브라우저 캐시 초기화를 CDN cold로 표현하지 않는다.
- Playwright routing 등 캐시 동작을 바꾸는 도구 사용 여부를 명시한다.
- A/B는 같은 준비 절차를 따른다. CDN 예열은 양쪽 동일하게 수행한다.
- Cold와 warm, 실제 사진과 SVG 결과를 합산하지 않는다.

주 실험은 실제 이미지 + warm으로 렌더링 차이를 확인하고, cold를 별도로 실행해 다운로드·디코딩을 포함한 사용자 경험을 확인한다.

## 6. 시나리오와 주요 지표

### A. 연속 스크롤

상단에서 10초 아래, 10초 위로 같은 입력 궤적을 실행한다. 중간 속도와 빠른 속도는 별도 시나리오로 고정한다.

- 주지표: 스크롤 구간 LoAF blockingDuration 합계.
- 보조: 긴 프레임 횟수·최대 길이, Long Task, rAF 간격.
- rAF 간격을 실제 표시 FPS로 부르지 않는다.
- LoAF 양쪽 0이면 해당 조건에서 프리즈 감소 증거 없음으로 결론 낸다.
- 입력은 브라우저 외부 입력 경로를 사용한다. 매 tick scrollTop 변경으로 대체하지 않는다.
- 실기기는 터치 입력을 사용하고 실제 입력 시각·이동 거리·목록 도달 범위를 기록한다.

### B. 빠른 이동 후 빈 영역

빠르게 아래로 이동, 방향 전환, 상단·중간·하단 정지를 포함한다.

- 주지표: 가시 영역에서 실제 사진 픽셀이 준비되지 않은 면적의 시간 적분(예: viewport 대비 비율×ms).
- 함께 보고: 빈 영역 episode 횟수, 각 지속 시간, 최대 면적.
- 의도된 skeleton도 사진 미표시 시간에는 포함하되 완전 공백과 별도 분류한다.
- 이미지 자체의 흰색 부분을 빈칸으로 판정하지 않는다.
- fixture의 기대 이미지 및 카드 영역을 기준으로 판정기를 만들고 사람이 표본을 검토한다.
- 초기 제안 episode 기준: 예상 사진 영역 10% 이상이 100ms 이상 미표시. 파일럿에서 검출 가능성을 확인한 뒤 본 실험 전에 확정한다.
- 검사한 프레임 사이에 짧은 빈칸이 생겼을 수 있으므로 0건은 미관측으로 표현한다.

### C. 스크롤 직후 사진 선택

정해진 이동 후 사전 고정한 간격에 사진을 선택한다. 실제 클릭 대상 ID와 예상 ID 일치를 확인한다.

서로 다른 시간을 분리해 측정한다.

1. 입력→시각적 피드백: 강조·로딩 표시·모달 틀 등 첫 반응이 실제 보인 시점.
2. 입력→올바른 확대 사진 표시: 선택한 사진이 모달의 의도된 영역에 실제로 보인 최초 관측 시점.
3. 입력→코드상 모달 준비: ID·visible·complete·naturalWidth·decode 조건 충족.
4. 실패율: 잘못된 사진, 모달 미열림, 이미지 오류, 제한 시간 초과.

주지표는 2번으로 한다. 3번은 원인 분석 보조이며 픽셀 표시 시점으로 대체하지 않는다.
표시 판정은 사진 영역의 점유와 fixture 일치를 사용하고 페이드 애니메이션의 판정 임계값을 사전에 정한다.

### D. 탐색 과제

예: 특정 날짜·장소의 사진을 찾아 확대하고 다시 목록으로 돌아오기.

- 완료 시간, 성공률, 오선택·되돌아가기 횟수.
- 과제 직후 불편 정도를 같은 질문과 척도로 수집.
- 이미지 위치 암기 효과를 줄이도록 난이도가 유사한 과제 세트를 교차 배정.
- 학습 효과, 참여자별 차이를 분석에 반영한다.
- 작은 사용자 평가만으로 전체 사용자 만족도 개선을 일반화하지 않는다.

## 7. 실제 화면 표시를 측정하는 방법

브라우저 내부 값만으로 실제 픽셀 표시 완료를 단정하지 않는다.

### 권장: 별도 시각 실험

- 120fps 이상 외부 카메라로 실기기 화면과 터치 동작을 함께 촬영한다.
- 입력 기준 프레임과 올바른 사진이 나타나는 프레임을 판독한다.
- 카메라 fps, 화면 주사율, 노출·롤링셔터 영향을 기록한다.
- 120fps는 프레임당 약 8.3ms이므로 이보다 정밀한 소수점 차이를 주장하지 않는다.
- 물리적 터치 시작과 브라우저 이벤트 수신은 다른 기준이다. 외부 영상 결과와 이벤트 기반 시간을 같은 지표로 합치지 않는다.
- 눈으로 터치 접촉 시점을 확정하기 어려우면 오차 범위로 보고하거나 동기화된 입력 장치를 사용한다.
- 두 평가자가 일부 영상을 독립 판독하고 불일치 규칙을 정한다.

### 대안: 브라우저 캡처·trace

- 프레임 캡처는 화면 결과 관측의 보조다. 캡처 시각과 간격을 보관하고 실제 디스플레이 제시 시간과 구분한다.
- 캡처가 성능에 영향을 줄 수 있으므로 캡처 on/off 파일럿을 수행한다.
- 시간 본 실험과 무거운 trace·영상 진단을 분리한다.
- 내부 두 번의 rAF 또는 decode 완료를 실제 표시 완료로 부르지 않는다.
- 외부 영상이 불가능하면 결과명을 캡처상 표시 지연으로 낮추고 한계를 명시한다.

## 8. 표본 수와 순서

각 고정 조건·시나리오마다 다음을 기본으로 한다.

- 파일럿: A/B 각 5회. 본 실험과 합산하지 않음.
- 본 실험: A/B 100쌍을 목표로 사전 고정. AB/BA 순서를 seed로 균형 무작위 배치.
- 실기기 영상 비용이 큰 경우 별도 30쌍으로 수행하되 중앙값·분포 중심으로 보고하고 p95 정밀 추정을 주장하지 않는다.
- 사용자 과제: 우선 8~12명으로 탐색적 평가. 확증적 평가에 필요한 인원은 최소 의미 효과와 파일럿 분산으로 별도 산정한다.
- 각 실행의 스크롤 수백 프레임을 독립 표본 수백 개로 세지 않는다.
- 중간 결과가 좋다는 이유로 조기 종료하지 않는다.
- 표본 확대는 본 실험 결과를 보기 전에 정하거나 새 실험으로 분리한다.

모든 조건의 전수 조합을 무작정 실행하지 않는다. 기본 셀부터 검증하고 전체 앱·실기기 셀로 재현한다. 핵심 셀과 확장 셀은 실행 전에 선언한다.

## 9. 통계와 의미 있는 개선의 판정

- 모드별 중앙값, IQR, p95, 실패 수/전체 시도 수를 함께 보고한다.
- 쌍별 차이와 95% 신뢰구간을 계산한다. 부트스트랩은 A/B 쌍 단위로 재표집한다.
- p95 차이도 쌍 구조를 유지해 불확실성을 계산하며, 표본 수에 따른 한계를 남긴다.
- 상대 감소율과 절대 차이를 함께 쓴다.
- 통계적 차이와 사용자에게 의미 있는 차이를 구분한다.

실용적 최소 차이는 사전 결정해야 한다. 다음은 파일럿·과제 맥락으로 검토할 초안이며 보편적 UX 기준이 아니다.

- 확대 사진 실제 표시 지연: 중앙값 50ms 이상 감소를 실용적 후보로 검토하되, 영상 해상도·기존 지연·사용자 과제 결과를 함께 판단.
- 빈 영역: episode 지속 시간과 면적×시간 감소를 우선 판단하고 실패 증가가 없어야 함.
- 스크롤: 실제 긴 프레임 부담이 존재하는 조건에서 차단 시간 감소가 확인돼야 함.
- 과제: 완료 시간과 성공률을 함께 판단. 빠르지만 오선택이 늘면 개선 판정 보류.

합성 조건에서만 좋아지면 합성 조건 개선으로 한정한다. 실기기에서 재현되고 기능 회귀가 없으면 모바일 재현 근거로 보고한다. 사용자 체감 개선은 과제·관찰 결과까지 있을 때 별도로 주장한다.

## 10. 실패 처리와 정합성

- 잘못된 이미지 선택, 이미지 요청 실패, 모달 timeout은 제품 실패로 남긴다.
- timeout을 삭제하고 성공한 실행의 평균만 보고하지 않는다. 성공 실행 지연과 전체 실패율을 병기한다.
- 인증 실패, 잘못된 fixture, 계측기 고장은 사전 규칙에 따라 무효 처리하고 이유·원본을 보존한다.
- 재실행은 원 실행을 덮어쓰지 않고 연결 ID를 둔다.
- 입력량, 이동 범위, 클릭 시점 차이가 큰 쌍은 사전 허용 범위에 따라 판정한다.
- A/B 한쪽에 유리하게 실패·이상치를 제거하지 않는다.
- 기능 검증: 사진 ID 일치, 정렬·필터 유지, 모달 닫기, 스크롤 복귀, 키보드 접근과 포커스 복귀도 별도 확인한다.

## 11. 결과 저장 구조

실제 실행 시 별도 날짜 폴더에 보관한다.

- protocol.md / protocol-lock.json: 가설, 주지표, 최소 의미 차이, 중단·무효 규칙
- environment.json: 기기·브라우저·전원·네트워크·캐시
- fixture-manifest.json: 이미지와 데이터 해시
- source/: A/B diff, 실행 코드, 커밋·빌드 정보
- schedule.json: seed와 실행 순서
- raw/: 입력·observer·네트워크·실패 원시 기록
- visual/: 영상, 판독표, 캡처 시각·불확실성
- summaries/: 조건별 표·신뢰구간
- REPORT.md: 결과, 무효·실패, 한계, 허용 가능한 이력서 문장

쿠키·인증 토큰·개인 사진은 결과 묶음에 포함하지 않는다.

## 12. 완료 기준과 이력서 반영

- [ ] 가상화 외 A/B 차이가 없음을 검토
- [ ] 실제 이미지 fixture와 고유 수 공개
- [ ] 주 실험과 파일럿·영상·trace 표본 분리
- [ ] 기능 실패와 무효 실행 전부 기록
- [ ] 실제 표시와 코드상 준비를 구분
- [ ] 기본 조건 및 전체 앱·실기기 재현 결과 구분
- [ ] 개선 없음·악화 결과도 보고
- [ ] 실제 사용자 INP, 60FPS 보장, 프리즈 완전 해결로 확대하지 않음
- [ ] 최종 숫자를 원시 자료에서 재계산 가능

측정 후 문장 예시:

“실제 썸네일 N개를 사용한 [기기·조건] A/B 실험 K쌍에서, 사진 선택부터 확대 사진이 화면에 보이기까지의 [중앙값/p95]를 A에서 B로 줄였습니다. 표시 시점은 [영상/캡처]으로 확인했습니다.”

효과가 확인되지 않은 경우:

“가상화로 렌더링 범위를 제한하고 실제 이미지 탐색·선택 흐름을 검증했습니다. 이번 조건에서는 사용자 경험 지표의 의미 있는 개선을 확인하지 못했습니다.”

이 설계는 테스트 실행이나 Preview 배포를 수행한 기록이 아니다.
